Meridian RFQ Pipeline — Sheet Inventory & ER Diagram

Data model behind the vendor-selection → RFQ dispatch → bid tracking → evaluation → shortlist pipeline

Sheet inventory

Two Google Sheets workbooks power the pipeline, referenced everywhere as MERIDIAN_VENDOR_SHEET_ID and MERIDIAN_SHEETS_BID_LOG_ID, split across nine tabs.

Workbook 1 — Vendor Master MERIDIAN_VENDOR_SHEET_ID

TabRangePurpose
VendorsA:RVendor master data — pricing, delivery, quality, risk, relationship history. Read by the selector and the evaluator.

Workbook 2 — Bid Log MERIDIAN_SHEETS_BID_LOG_ID

TabRangePurpose
WorkOrdersA:HIncoming work orders that trigger an RFQ
RFQEventsA:GOne row per RFQ dispatch event, keyed to a work order
RFQInvitesA:IThe 8 vendors selected/invited per RFQ
EmailLogA:GGmail thread/message tracking per vendor per RFQ
BidsA:NParsed bid data extracted from vendor reply emails
BidEvaluationA:NScored/ranked bids per RFQ
ShortlistA:LFinal top-5 vendors per RFQ, with justification
DisputesA:FOpen disputes per vendor, used to disqualify vendors during selection

Schema notes / open questions for the team

Bids ↔ BidEvaluation is drawn 1-to-0/1 Evaluation only happens after all bids for an RFQ are in — but that's a process convention enforced by the skill logic, not a real constraint in the sheet. Nothing stops a bid existing without ever being evaluated.
EmailLog and Bids aren't hard-linked by a shared key The tracker skill correlates them by gmail_thread_id and vendor_id at runtime, and separately does a raw subject-line mailbox search to catch unsolicited bids that never appear in EmailLog at all. If this moves onto a real relational database, we'd want an explicit bids.email_log_id foreign key.
RFQEvents and RFQInvites overlap heavily Both are effectively per-RFQ-per-vendor rows, just written by different pipeline phases. In a normalized schema these would likely collapse into a single rfq_invites table with a status column instead of two parallel tabs.

Suggested next step

If we move this off Google Sheets onto a real database (e.g. as part of the Joule port, backed by HANA/CAP instead of Sheets destinations), the three points above should be resolved first — a normalized version would merge RFQEvents/RFQInvites, add the missing EmailLog→Bids foreign key, and make the evaluation relationship enforceable rather than conventional.
